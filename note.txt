Implement the Claims Proof submission flow in the Rewards Service.

Scope:
- Implement ONLY Claims Proof processing.
- Do NOT implement self-attestation, redeem, member proof, or other fulfillment types.
- Do NOT implement activity assignment logic yet.
- Follow the existing project architecture, coding conventions, service/repository patterns, GraphQL/API patterns, exception handling, and transaction patterns.

Functional flow:

1. Add a Claims Proof submission API/service operation in Rewards Service.
2. The request should contain the information required to identify the member activity:
   - memberId
   - programId
   - activityCode
   - completionDate
   - claimId
   - providerName
   - providerLocation
   - source
3. Find the corresponding member activity using the existing member/activity identification pattern.
4. Validate that the member activity exists and can accept a Claims Proof fulfillment.
5. Read the activity's `fulfillment_requirements` JSONB.
6. Locate the fulfillment whose `rule.fulfillmentType` is `CLAIMS_PROOF`.
7. Update only the runtime state of that Claims Proof fulfillment:
   - status = COMPLETED
   - completionSource = source
   - completedAt = completionDate
   - completionInfo = {
       referenceId: claimId,
       completionDate: completionDate,
       providerName: providerName,
       providerLocation: providerLocation
     }
8. After updating the Claims Proof fulfillment, evaluate the fulfillment requirements:
   - If all required fulfillments are completed:
       - fulfillment_status = COMPLETED
       - activity_status = COMPLETED
       - invoke the existing reward issuance flow.
   - Otherwise:
       - fulfillment_status = PENDING
       - keep the activity status unchanged.
9. Do not modify reward_status directly. Use the existing reward issuance flow.

Fulfillment JSON structure to support:

{
  "fulfillments": [
    {
      "rule": {
        "fulfillmentType": "CLAIMS_PROOF",
        "required": true,
        "ruleOrder": 1
        // remaining rule definition fields are preserved
      },
      "status": "PENDING",
      "completionSource": null,
      "completedAt": null,
      "completionInfo": null
    }
  ]
}

Important:
- `rule` contains the rule-definition snapshot.
- Do NOT introduce `ruleId` lookup for processing. The full rule definition is expected to be stored in the member activity JSONB.
- Do not add a separate fulfillment table.
- Keep `fulfillment_status` as a physical column on `rewards_member_activities`.
- Do not add `fulfillmentStatus` inside the JSONB; the physical column is the source of truth for overall fulfillment status.
- Claims Proof is the only fulfillment type that needs to be processed in this implementation.

Database migration:

    2. `fulfillment_requirements` JSONB

Implementation requirements:

- Keep the implementation extensible so additional fulfillment types can be added later, but do not implement them now.
- Handle duplicate/repeated Claims Proof submissions safely according to the project's existing idempotency/error-handling patterns.
- Use a transaction for the Claims Proof update and activity/fulfillment status evaluation.
- Add/update unit and integration tests following the existing project test patterns.
